# Live ZMK keymap HUD research

Research date: 2026-11-16. Sources below are project-authored documentation, mostly moving `main` branches. No app, firmware, signing status or hardware combination was independently tested; a README may describe features newer than a packaged release.

## Context and recommendation

The local config pins upstream ZMK to `4dd95d7840eb3d5a3f59bb29fbf1ab054715ef85`, dated 2026-10-19 in the manifest. Its build lists `xiao_ble//zmk` with `totem_left` and `totem_right`. The local `draw/keymap.yaml` is a curated keymap-drawer document, references `draw/totem-layout.json`, and contains ten named layers. Miryoku uses C macros and includes. No files in that config were changed for this research.

**Rafael Romão's [ZMK Layer HUD](https://github.com/rafaelromao/zmk-layer-hud) is the best documented match:** a panel draggable to another screen, actual keyboard-reported layer state, and reuse of keymap-drawer. This is an assessment, not a compatibility certification. His [firmware setup](https://github.com/rafaelromao/zmk-layer-hud/blob/main/docs/zmk-setup.md) requires a ZMK revision after February 2026; the manifest's October 2026 pin looks new enough, but build and real hardware tests remain necessary. It is a small, recently active open-source project rather than a widely established product. The inspected GitHub page showed 6 stars; a star count is only a rough indicator, not a quality measure.

## Rafael HUD setup to evaluate

Pin the HUD module to an explicitly reviewed immutable commit compatible with the chosen host version; project examples use floating `main`, and no suitable exact module commit was independently verified during this research. Keep the existing ZMK and Zephyr pins until a clean build proves compatibility. Add `rafaelromao/zmk-layer-hud` in `config/west.yml`; add a root devicetree node with `compatible = "zmk,layer-signal"; heartbeat-ms = <2000>;`. The optional `positions;` enables per-key lighting but exposes every physical press and release. For USB, add `snippet: layer-hud-usb-uart` to the **central** build entry. The module's `CONFIG_ZMK_LAYER_SIGNAL_GATT` defaults on when `CONFIG_BT_PERIPHERAL` is enabled for BLE. Build/flash central; its sibling need not change according to the project. GATT notifications require bonding/encryption and go only to the selected host; USB signals require the snippet, particularly when USB becomes the selected output. Re-pairing can be needed if macOS caches old BLE services. Source: [firmware setup](https://github.com/rafaelromao/zmk-layer-hud/blob/main/docs/zmk-setup.md).

On the host, set `keymap:` in the HUD config to the existing drawer YAML, then import the local repo and check the generated `config.imported.yaml` for undecided ZMK layer IDs. Correct layer mapping in the HUD config. If the drawing's key order differs from the firmware's, supply the appropriate `positions:` mapping. Check that `draw/totem-layout.json` resolves and all ten layers and 38 keys render correctly; no import was performed here. The README documents `sync` and `sync --watch` for updates. See [taking it from the keyboard repo](https://github.com/rafaelromao/zmk-layer-hud#taking-it-from-your-keyboards-repo).

The project distributes source plus an installer, rather than a documented Apple-notarized downloadable application. Its README describes `curl ... | sh`, which fetches the newest release by default and creates a virtual environment, installs dependencies, and may offer privileged operations. Review and pin the source and dependencies before running. Neither signing nor notarization of the resultant local app was verified. [Installation](https://github.com/rafaelromao/zmk-layer-hud#quick-start).

## Privacy and macOS permissions

HUD layer data alone can reveal the user's mode. Optional position messages combined with the keymap can reveal typed content. If key illumination is unnecessary, omit `positions;` from firmware. For BLE, the host process requires Bluetooth access. The HUD separately reads HID reports containing typed characters for a strip and modifier state; that requires macOS Input Monitoring. The README says the layer and position channel continues if HID access is unavailable, but that is not proof it never attempts access. The README documents `feed --no-hid-keys` for the standalone feed, not a verified equivalent setting for the native panel; do not represent this flag as a confirmed GUI switch. `feed --no-keys` is a different standalone-feed flag which suppresses both positions and typed characters. [Commands and permissions](https://github.com/rafaelromao/zmk-layer-hud#commands), [troubleshooting](https://github.com/rafaelromao/zmk-layer-hud#troubleshooting).

By default the HUD tracks typing statistics and writes per-key/layer session counts, but says it does not retain typed text in order and nothing leaves the machine; use `feed.sessions: 0` in its config to disable saved session files. Secure-input detection is a best-effort protective feature, not proof that all secret-entry paths are covered; the README notes some terminal and remote prompts may not be detected. `feed --raw` logs sensitive key events. A token protects its local WebSocket; anyone with access to the token could access its stream. [Sessions and limits](https://github.com/rafaelromao/zmk-layer-hud#sessions).

The Viewer README explicitly says its app is not notarized, suggests Gatekeeper's Open Anyway or removing quarantine, and claims no additional macOS permission for its full Raw HID setup. Its use of position reports still carries potentially sensitive information. Do not treat source availability, notarization, or permission prompts as a security audit. Verify the downloaded artifact and the actual signing state independently before authorizing execution. [Viewer README](https://github.com/Intersebbtor/ZMK-keymap-viewer/blob/main/README.md#-installation).
